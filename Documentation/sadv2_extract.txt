1.3  Definitions,  Acronyms,  and  Abbreviations  
 
Term  Definition  
Access  token  Short-lived  JWT  issued  at  login;  sent  with  API  requests  to  authorize  access  to  protected  resources.  
Active  Canonical  listing  status  for  a  live,  publicly  searchable  vehicle  listing  (replaces  informal  “LIVE”  in  earlier  drafts).  
ADR  Architecture  Decision  Record,  a  documented  significant  design  choice  with  context,  decision,  consequences,  and  alternatives.  
ALB  Application  Load  Balancer,  optional  AWS  load  balancer  used  for  internal  (east-west)  HTTP  routing  between  services.  
API  Gateway  AWS  managed  HTTP  entry  point;  the  public  gateway  handles  browser  traffic  (north-south);  a  private  internal  gateway  handles  service-to-service  calls  (east-west).

AWS  Amazon  Web  Services,  cloud  platform  hosting  all  production  components  except  the  external  Groq  LLM  API.  
Chunk  A  group  of  100  inventory  rows  processed  together  as  one  Step  Functions  Map  iteration.  
Choice  state  A  Step  Functions  construct  that  branches  execution  based  on  a  condition,  with  no  Lambda  invocation  or  cost.  
Cold  start  The  added  latency  incurred  when  AWS  Lambda  must  initialize  a  new  execution  environment.  
Confidence  score  Measure  of  parse/normalization  certainty.  In  ETL,  the  minimum  required-field  score  for  a  row;  in  search,  based  on  token  coverage  and  numeric  signals.  Rows/queries  below  0.6  may  invoke  Groq  fallback.  
DLQ  Dead-Letter  Queue,  Amazon  SQS  queue  where  messages  are  routed  after  repeated  processing  failures.  
DTO  Data  Transfer  Object,  validated  request/response  shape  used  at  NestJS  controller  boundaries.  
East-west  traffic  Service-to-service  HTTP  calls  within  the  AWS  VPC  (e.g.,  Admin  Service  ->  Auth  Service  via  internal  API  Gateway).  
ECR  Amazon  Elastic  Container  Registry,  stores  Docker  images  deployed  to  AWS  Lambda.  
ETL  Extract,  Transform,  Load  ,  the  automated  pipeline  that  turns  a  dealer’s  raw  CSV/JSON/ZIP  upload  into  validated,  searchable  listings.  
FR  /  NFR  Functional  Requirement  /  Non-Functional  Requirement,  identifiers  from  the  SRS  traceable  to  SAD  elements.  
Groq  External  LLM  inference  provider  used  as  a  fallback  normalizer  for  low-confidence  ETL  rows  and  unresolved  natural-language  search  tokens,  never  the  primary  parser.  
Human-in-the-loop  Design  gate  requiring  dealer  review  before  AI-inferred  listing  data  is  published;  ETL-loaded  listings  enter  pending_review  until  confirmed.

JWT  JSON  Web  Token  -   stateless  bearer  token  encoding  user  identity  and  role  claims;  validated  locally  by  each  service  using  a  shared  public  key  (NFR-13).

MarketplaceVehiclesWriteAdapter  
Sole  application  class  permitted  to  exercise  the  ADR-002  cross-schema  write  grant  into  marketplace.vehicles  and  marketplace.vehicle_images.  
MiniLM  The  all-MiniLM-L6-v2  sentence-embedding  model  used  to  generate  384-dimensional  vectors  for  semantic  search  and  listing  embeddings.  
Model-parity  constraint  Non-negotiable  requirement  that  ingestion  and  search  use  the  same  normalization  dictionaries  and  embedding  model/library  version  (FR-22.1,  NFR-26.1).  
NestJS  TypeScript  backend  framework  used  for  all  microservices;  enforces  layered  structure  (controllers,  services,  repositories,  adapters).  
NIC  National  Identity  Card  :  verification  document  required  for  Individual-tier  dealer  registration.  
North-south  traffic  Client  browser  to  backend  traffic  via  the  public  API  Gateway  over  HTTPS.  
Pending  review  Listing  status  after  ETL  Load;  not  publicly  searchable  until  the  dealer  explicitly  confirms  AI-inferred  data  (FR-43).

pgvector  PostgreSQL  extension  enabling  storage  and  similarity  search  over  vector  embeddings  (vector(384)  on  listings).  
Provenance  Metadata  recording  whether  a  field’s  value  came  from  deterministic  rules  or  LLM  inference,  and  with  what  confidence.  
RBAC  Role-Based  Access  Control  :  authorization  enforced  via  JWT  role  claims  and  NestJS  RolesGuard  (Guest,  Buyer,  Dealer,  Administrator).  
RDS  Amazon  Relational  Database  Service  :  hosts  the  shared  PostgreSQL  instance  with  schema-per-service  isolation  (ADR-001).  
RDS  Proxy  Connection  pooler  between  Lambda  functions  and  RDS;  required  to  bound  database  connections  under  Step  Functions  Map  concurrency  (NFR-10).  
Refresh  token  Long-lived  opaque  token  used  to  obtain  new  access  tokens  without  re-login;  stored  hashed  server-side  and  revocable  on  logout  (FR-05).  
Rejected  records  Table  (ingestion.rejected_records)  storing  rows  that  fail  validation  after  rules  and  AI  normalization,  with  actionable  error  reasons.

Rules-first  normalization  
Deterministic  dictionary/regex/pg_trgm  parsing  applied  before  any  LLM  call;  Groq  invoked  only  when  confidence  falls  below  0.6  (ADR-004).  
S3  Amazon  Simple  Storage  Service  :  stores  immutable  raw  uploads  (raw/),  staging  JSON  between  ETL  states  (staging/),  dealer  verification  documents,  and  processed  vehicle  images.  
Schema-per-service  Logical  database  isolation  model:  one  RDS  instance,  five  service-owned  schemas  (auth,  marketplace,  ingestion,  notification,  admin),  each  with  a  dedicated  PostgreSQL  role.  
SES  Amazon  Simple  Email  Service  :  sends  transactional  email  notifications  (upload  complete/fail,  dealer  approval,  etc.).  
SPA  Single  Page  Application  :  React  web  frontend  served  from  S3/CloudFront.  
SQS  Amazon  Simple  Queue  Service  :  durably  buffers  upload  job  messages  between  the  Ingest  API  and  Step  Functions.  
SSM  AWS  Systems  Manager  Parameter  Store  :  stores  configuration  and  secrets  (e.g.,  JWT  keys,  Groq  API  key)  alongside  Secrets  Manager.  
State  machine  An  AWS  Step  Functions  execution  orchestrating  a  sequence  of  Lambda  invocations  and  branching  logic  for  one  upload  job.  
Step  Functions  AWS  orchestration  service  coordinating  the  eleven  ETL  Lambda  stages  per  upload  with  declarative  Retry/Catch  (ADR-003).  
Terraform  Infrastructure-as-code  tool  used  in  cloud-infrastructure  for  reproducible  AWS  provisioning  and  deployment.  
vehicle_dictionaries  Marketplace-owned  reference  table  (makes,  models,  fuel,  transmission,  aliases)  backing  pg_trgm  fuzzy  matching;  read  by  Ingestion  via  scoped  grant  and  in-memory  cache.  
VPC  Virtual  Private  Cloud  :  network  boundary  enclosing  Lambda  functions,  RDS,  and  internal  API  Gateway.

4.1.2  Bulk  Upload  Intake  
Use  case  name  Bulk  Upload  Intake  
Actor(s)  Dealer  
 Confidential  ©AutoVault  LK,  2026  Page  41  of  75   
Description  A  verified  Business  Dealer  submits  a  CSV/JSON  inventory  file  and  a  ZIP  of  vehicle  images.  The  system  stores  the  raw  files  and  starts  asynchronous  processing  without  blocking  the  dealer's  request.  
Preconditions  The  Dealer  is  authenticated,  possesses  a  valid  JWT,  and  has  an  approved  Business-tier  profile.  
Main  flow  1.  The  Dealer  submits  the  CSV/JSON  file  and  image  ZIP  via  the  frontend.  
2.  The  Ingest  API  (Ingestion  and  ETL  Service)  verifies  the  JWT  locally  against  a  shared  public  key,  avoiding  a  network  call  to  the  Auth  Service.  
3.  The  API  performs  a  format-only  check  (validating  it  is  parseable  CSV/JSON  and  a  real  ZIP  archive).

5.  The  API  creates  an  upload_jobs  row  in  PostgreSQL  (ingestion  schema)  with  a  PENDING  status.

Successful  end/post  condition  
An  upload_jobs  record  exists  with  status  PENDING,  raw  files  are  durably  stored  in  S3,  and  the  payload  is  queued  in  SQS  awaiting  Step  Functions  execution.  
Fail  end/post  condition  
If  the  files  fail  the  format-only  check,  the  request  is  rejected  synchronously  with  a  clear  reason,  and  no  job  or  queue  message  is  created.  
Contributing  design  elements  
Ingestion  and  ETL  Service,  Amazon  S3,  Amazon  SQS,  PostgreSQL  (ingestion  schema).

 Confidential  ©AutoVault  LK,  2026  Page  42  of  75   
Use  case  name  Process  and  Review  Pending  Listings  
Actor(s)  Dealer  
Description  Following  a  bulk  upload,  an  automated  ETL  pipeline  orchestrates  the  chunking,  normalization,  and  embedding  of  data  using  targeted  AWS  Lambda  functions.  All  accepted  rows  are  persisted  as  PENDING_REVIEW  listings.  The  Dealer  then  completes  the  use  case  by  explicitly  reviewing  and  confirming  any  AI-inferred  data  before  the  listings  are  published.  
Preconditions  The  Dealer  has  successfully  initiated  the  "Bulk  Upload  Intake"  use  case,  and  the  asynchronous  AWS  Step  Functions  execution  is  underway.  
 Confidential  ©AutoVault  LK,  2026  Page  43  of  75   
Main  flow  1.  The  validateFile  function  Lambda  checks  headers  and  file  integrity  once  for  the  entire  file.  
2.  The  splitChunks  function  Lambda  divides  the  file  into  100-row  chunks,  passing  S3  descriptor  pointers  to  a  parallel  Map  state.  
3.  Inside  the  Map  state,  the  parseNormalize  function  Lambda  applies  a  6-step  normalizer  to  each  field  and  calculates  a  row-level  confidence  score.  
4.  If  the  confidence  score  is  <  0.6,  the  groqNormalize  function  Lambda  routes  unresolved  fields  to  the  external  Groq  API  (LLM)  for  contextual  inference,  subsequently  dropping  any  hallucinated  values.  
5.  The  validateRows  function  Lambda  validates  mandatory  business  rules;  rows  failing  this  step  are  written  to  rejected_records.  
6.  The  enrich  function  Lambda  maps  JSONB  specifications  based  on  vehicle  type  and  builds  the  final  search_text.  
7.  The  embed  function  Lambda  generates  a  384-dimensional  vector  embedding  using  the  all-MiniLM-L6-v2  model.  
8.  The  Load  function  Lambda  executes  a  bulk-insert,  saving  accepted  rows  into  the  marketplace.vehicles  table  with  a  PENDING_REVIEW  status.  
9.  The  Dealer  opens  the  dashboard,  reviews  the  AI-inferred  fields,  and  confirms  the  data,  transitioning  the  listing  status  to  LIVE.  
 Confidential  ©AutoVault  LK,  2026  Page  44  of  75   
Successful  end/post  condition  
Valid  rows  exist  as  LIVE  searchable  listings,  rejected  rows  are  recorded  with  actionable  reasons,  and  the  dealer  has  explicitly  confirmed  all  AI-inferred  data.  
Fail  end/post  condition  
If  the  Groq  API  is  unavailable,  the  pipeline  catches  the  error  and  proceeds  to  validation  using  rules-only  data,  degrading  gracefully  rather  than  failing  the  entire  batch.  
Contributing  design  elements  
AWS  Step  Functions,  ETL  Lambdas  (validateFile  function,  splitChunks  function,  parseNormalize  function,  groqNormalize  function,  validateRows  function,  enrich  function,  embed  function,  Load  function),  Amazon  S3,  Groq  API,  PostgreSQL,  Marketplace  Service.  
4.1.4  Intelligent  Search  Execution  
Use  case  name  Intelligent  Search  Execution  
Actor(s)  Buyer,  Guest  
Description  A  user  searches  the  marketplace  using  a  free-text  natural-language  query.  The  system  utilizes  a  5-stage  deterministic  parser,  an  LLM  fallback,  and  semantic  embeddings  to  return  a  highly  accurate,  ranked  result  list.  
Preconditions  None.  The  feature  is  available  to  both  authenticated  Buyers  and  unauthenticated  Guests.  
 Confidential  ©AutoVault  LK,  2026  Page  45  of  75   
Main  flow  1.  The  user  submits  a  free-text  query  via  the  frontend  search  bar.  
2.  The  Marketplace  Service  tokenizes  the  query,  masks  stopwords,  and  executes  Stage  1  (Multi-word  phrase  extraction)  and  Stage  2  (Numeric  pattern  extraction).  
3.  The  service  executes  Stage  3  (Exact  Dictionary  Hits)  and  Stage  4  (Fuzzy  dictionary  hits  via  pg_trgm),  strictly  resolving  Make  before  Model.  
4.  The  service  calculates  a  confidence  score  based  on  coverage  and  numeric  signals.  
5.  If  the  confidence  score  is  <  0.6,  unresolved  tokens  and  a  shortlist  of  candidates  are  sent  to  the  Groq  API  for  LLM-assisted  filter  extraction.  
6.  All  returned  LLM  fields  are  strictly  whitelist-validated  against  the  database  schema.  
7.  The  service  passes  the  remaining  unconsumed  semantic  text  to  the  embedding  library  to  produce  a  query  vector.  
8.  The  service  executes  a  single  PostgreSQL  query  combining  exact  filter  conditions  (WHERE  clauses)  and  pgvector  semantic  ranking  (ORDER  BY  embedding  <=>  vector).  
9.  Ranked,  paginated  results  are  returned  to  the  user.  
Successful  end/post  condition  
A  ranked  list  of  matching  listings  is  returned,  and  a  record  is  logged  in  the  search_queries  table  to  fuel  future  alias  promotion.  
Fail  end/post  condition  
If  the  query  returns  zero  results,  the  system  executes  an  automated  relaxation  path  (widening  numeric  ranges  or  dropping  non-essential  filters)  before  returning  an  empty  state.  
Contributing  design  elements  
Marketplace  Service,  Groq  API,  PostgreSQL  (marketplace  schema,  utilizing  pg_trgm  and  pgvector).
