## Listings & Ingestion (FR-13 – FR-15)

### FR-13 — Dealers create/update/deactivate listings ✅
- `marketplace-service/src/modules/listings/controllers/listing.controller.ts` — `POST /listings`, `PATCH /listings/:id`, `PATCH /listings/:id/deactivate`
- `marketplace-service/src/modules/listings/services/listing.service.ts:30-109` — `createListing`, `updateListing`, `deactivateListing`
- `marketplace-service/src/modules/listings/repositories/listing.repository.ts:15-80`
- Standard TypeORM CRUD over the `Vehicle` entity, JWT + role guards (`DEALER`/`ADMIN`), ownership enforced in `ListingService.assertOwnership` (`listing.service.ts:115-123`).

### FR-13.1 — Regenerate search_text/embedding on searchable-field edits ❌
- Checked: `listing.service.ts:69-88` (`updateListing`), `listing.repository.ts:47-69` (`update`)
- `ListingRepository.update()` copies only plain DTO columns (make, model, price, specs, etc.) — never touches `vehicle.entity.ts`'s `searchText` (line 114) or `embedding` (line 122) columns. No embedder/search-text builder is called anywhere in the listings module.

### FR-13.2 — Old embedding must not remain searchable post-edit ❌
- Same files as FR-13.1. Direct consequence of that gap: since embedding/search_text are never rewritten on update, a stale embedding stays searchable indefinitely.

### FR-14 — Async consumption of `VehicleChunkProcessed` events for bulk insert ❌
- No SQS/SNS client or consumer code anywhere in `marketplace-service/src` (only `infrastructure/aws/.gitkeep`).
- `ingestion-service/src/workers/etl-worker/**` and `ingestion-service/src/lambda/**` are empty `.gitkeep` scaffolds — nothing publishes `VehicleChunkProcessed` either.
- Only hint of intent: `upload_job_id` FK column on `Vehicle` (`vehicle.entity.ts:33`). Neither producer nor consumer exists.

### FR-15 — Core relational columns + JSONB `specs` for category-specific attributes ✅
- `marketplace-service/src/infrastructure/database/entities/vehicle.entity.ts:25-144`, `specs` JSONB column at line 109
- `marketplace-service/src/modules/search/constants/known-spec-keys.constants.ts` — backing dictionary of allowed spec keys
- Core fields (make, model, price, mileage, fuelType, transmissionType) are typed columns; type-specific attributes (body_type, seats, doors, drive_type) live in `specs: Record<string, unknown>`.

## Favourites & Dealer Profiles (FR-16 – FR-18.1)

### FR-16 — Buyers save/remove favourites ❌

- `marketplace-service/src/modules/favourites/{controllers,dto,entities,repositories,services}` — all `.gitkeep` placeholders, no module registration
- Schema is scaffolded; zero business logic or API surface.

### FR-17 — Buyers retrieve favourites list ❌
- Same empty `favourites` module as FR-16.

### FR-18 — Dealer profile summaries alongside listings ✅
- `marketplace-service/src/modules/dealers/services/dealer.service.ts`, `repositories/dealer.repository.ts:18-60` (`findById`/`toSummary`)
- Consumed by `listing.service.ts:125-155` (`withDealer`/`toDealerPayload`) and inlined in search results via `vehicle-search.repository.ts:49-55` (`DEALER_JOIN`/`DEALER_COLUMNS`)
- Both listing detail and search results attach a dealer summary (business name, owner, city, phone, verification badge).

### FR-18.1 — Consume `DealerApproved` events into a local dealer read model ⚠️
- `marketplace-service/src/infrastructure/database/entities/auth-user.view-entity.ts`, `dealer-profile.view-entity.ts:6` — `@Entity({ schema: 'auth', name: 'dealer_profiles', synchronize: false })`
- Queried directly in `dealer.repository.ts:27-43` and joined cross-schema in `vehicle-search.repository.ts:49-51` (`auth.dealer_profiles`)
- **Design deviation, not a simple gap**: no event consumer or local read model exists — the codebase reads live cross-schema instead. `Documentation/plan-a-strict-isolation.md` and `plan-b-reads-cross-schemas.md` show this was a deliberated tradeoff; the code landed on Plan B (cross-schema reads) rather than FR-18.1's event-sourced replication.

## Search (FR-19 – FR-24)

### FR-19 — Structured filter search (make, model, price, mileage, fuel, transmission) ✅
- `marketplace-service/src/modules/search/filters/filter-query.builder.ts`, `dto/filter-search.dto.ts`
- `services/filter-search.service.ts:34-88`, `repositories/vehicle-search.repository.ts:135-169`
- Includes a zero-result relaxation ladder (`filter-search.service.ts:112-199`) and per-dimension facet counts (`vehicle-search.repository.ts:201-240`).

### FR-20 — Paginated, sortable results ✅
- `filter-search.service.ts:45-46` (page/limit, `DEFAULT_PAGE_SIZE`/`MAX_PAGE_SIZE`)
- `vehicle-search.repository.ts:145-146,155-166` (LIMIT/OFFSET)
- `filters/sort-clause.ts:1-37` — `buildOrderBy`, `SortOption`: relevance / price_asc / price_desc / year_desc / mileage_asc / newest

### FR-21 — Deterministic rule-based NL parser (dictionary + pg_trgm) ✅
- `marketplace-service/src/modules/search/parser/deterministic-parser.ts:55-71` — `parseQuery`, 5-stage pipeline (phrases → numeric specs → numeric → exact → fuzzy)
- `parser/vocabulary.ts` (trigram fuzzy matching), `parser/tokenize.ts`, `repositories/vehicle-dictionary.repository.ts`

### FR-21.1 — Confidence = consumed / meaningful tokens ✅
- `deterministic-parser.ts:277-294` (`finalize`) — `confidence = consumedCount / meaningfulCount` (line 282-283)

### FR-21.2 — Below 0.6 threshold routes to Groq fallback ✅
- `parser/types.ts` — `CONFIDENCE_THRESHOLD`, applied at `deterministic-parser.ts:290` (`needsGroqFallback: confidence < CONFIDENCE_THRESHOLD`)
- `groq/groq-fallback.service.ts:17-34` — explicitly cites "FR-21.2 ... Groq only when the rules parser is below 0.6"

### FR-21.3 — Validation layer drops hallucinated Groq output ✅
- `marketplace-service/src/modules/search/groq/groq-whitelist.ts` — `whitelistGroqOutput`, `mergeFilters`
- Used in `groq-fallback.service.ts:41-51`, logs `Groq whitelist dropped: ...` for rejected values

### FR-21.4 — Log unresolved tokens + Groq corrections; promote frequent corrections to vocabulary 🟡
- **Logging (done):** `filter-search.service.ts:201-228` (`logSearch`) inserts `raw_text`, `unresolved_tokens`, `confidence`, `used_llm` into `marketplace.search_queries`
- **Promotion (missing):** `vehicle-dictionary.entity.ts:50-58` has an `aliases: string[]` JSONB column with a comment stating it is "grown by the alias-promotion loop" — but no code writes to `aliases`, no batch job aggregates `search_queries`, and no promotion service exists anywhere (`grep -r "promot"` across `src` returns only that entity comment).
- Stated intent in `Documentation/Project Proposal and Feasibility (1).md:455` and the architecture-plan docs; schema column reserved, logic never built.

### FR-22 — Query embedding for semantic matching ✅
- `marketplace-service/src/modules/search/services/query-embedding.service.ts:13-43` — `QueryEmbeddingService.embedQuery`
- Backed by `shared/normalize-embed/embedder.ts:20-30` — `createXenovaEmbedder` (MiniLM via `@xenova/transformers`)

### FR-22.1 — Identical embedding model/version/pooling/normalization for ingestion and query, via one shared library 🟡
- `marketplace-service/src/shared/normalize-embed/{embedder.ts,vector.ts,constants.ts,index.ts}` — the shared lib: `pooling: 'mean'`, `normalize: true` (`embedder.ts:26`), `l2Normalize`/`assertEmbedding` (`vector.ts`), single `EMBEDDING_MODEL_ID` constant (`constants.ts`)
- `ingestion-service/src/lambda/embed/` and `ingestion-service/src/workers/etl-worker/pipeline/embeddings/` are empty `.gitkeep` scaffolds — no ingestion-side embedder exists to consume this shared lib.
- The library is *designed* for parity (single model-ID constant, shared pooling function), but with no ingestion-side embedding generation, "same model on both sides" is currently unverifiable/moot.

### FR-22.2 — Model change requires full re-embedding; no partial migration ❌
- Checked `database/src/migrations` and `shared/normalize-embed/constants.ts` for a version column or re-embed job.
- No `embedding_model_version` column on `vehicles`, no migration/backfill script, no versioning metadata anywhere. A model swap today would silently mix incompatible vector spaces with no detection.

### FR-23 — Single query combining WHERE filters + `ORDER BY embedding <=> query_vector` ✅
- `vehicle-search.repository.ts:159-166` — one `SELECT ... WHERE ... ORDER BY ...` combining `buildFilterQuery`'s WHERE with `buildOrderBy`
- `filters/sort-clause.ts:24-26` — `v.embedding <=> $N::vector ASC`
- `filters/search-rank.ts:94-100` — `appendTrigramWhere` also gates embedding distance in WHERE (`v.embedding <=> $eIdx <= $dIdx`), added this session to stop irrelevant results (e.g. bikes) from surfacing on vague semantic queries

### FR-24 — Graceful degradation (Groq failure → rules+trigram; full filter match → skip semantic) ✅
- `groq-fallback.service.ts:64-68` — catch-all returns rules-only result on Groq failure
- `search/filters/search-rank.ts:41-81` — `chooseSearchRank`: vector first, pg_trgm fallback if no embedding, skips ranking entirely when filters are fully resolved with no leftover text
- `query-embedding.service.ts:29-36` — catches ONNX/model-load failures, returns `null` so ranking is skipped rather than failing the request

### FR-25 — Related/recommended listings on vehicle detail page ❌
- `vehicle-search.repository.ts:249-286` (`findById`) returns only the requested vehicle — no related-listings query
- `marketplace-service/src/modules/recommendations/{controllers,dto,entities,repositories,services}` — all empty `.gitkeep` scaffolds, not wired into any module

## Guest Access, Dealer Uploads, Admin (FR-54 – FR-59)

### FR-54 — Guests browse/search without registering ✅
- `marketplace-service/src/modules/search/controllers/search.controller.ts` — no auth guard on `@Controller('search')` or its routes
- `web-frontend/src/pages/SearchPage.tsx`, routed unauthenticated in `web-frontend/src/App.tsx`
- `/filters` and NL-search endpoints are public; `SearchPage`/`HomePage` routes carry no `RequireAuth` wrapper.

### FR-55 — Guest prompted to log in when saving a favourite ✅
- `web-frontend/src/components/search/SaveButton.tsx:13-18` — checks `isAuthenticated`, shows a toast ("Sign in to save listings"), redirects to `/login`
- `web-frontend/src/auth/RequireAuth.tsx` — also gates the `/saved` page itself

### FR-56 — Dealer drag-and-drop bulk upload (CSV/JSON/ZIP) ❌
- No dealer upload page under `web-frontend/src/pages/dealers` (only `DealerLoginPage.tsx`, `DealerRegisterPage.tsx`) and no route for one in `App.tsx`
- `ingestion-service/src/modules/ingestion/*` and `ingestion-service/src/lambda/ingest-api/*` are empty `.gitkeep` scaffolds, not registered in `ingestion-service/src/app.module.ts` (which only wires `HealthModule`)
- Only DB entities exist (`upload-job.entity.ts`, `etl-stage-log.entity.ts`, `rejected-record.entity.ts`) — neither the UI nor a working backend endpoint exists.

### FR-57 — Dealer polled upload progress + row-level error reports ❌
- No dealer-facing UI; `ingestion-service/src/modules/job-status/*` is empty scaffolding, not registered in `app.module.ts`
- The only adjacent UI, `web-frontend/src/pages/admin/AdminUploadsPage.tsx`, is **admin-facing** (all dealers' jobs), fetches once via `useAsyncData` with no polling (no `setInterval`/refetch), and shows only aggregate valid/invalid counts — not row-level errors, and not scoped to a single dealer.

### FR-58 — Dealer manage (edit/deactivate) own listings via frontend ❌
- `web-frontend/src/pages/dealers/` only contains `DealerLoginPage.tsx` and `DealerRegisterPage.tsx`
- No listing management component anywhere under `web-frontend/src/components` or `pages`, no route in `App.tsx`
- Note: the *backend* API for this exists and works (FR-13's `ListingController`) — only the dealer-facing UI to drive it is missing.

### FR-59 — Admin dashboard: user management, upload monitoring, audit logs ✅
- `web-frontend/src/pages/admin/{AdminDashboardPage,AdminUsersPage,AdminUploadsPage,AdminAuditLogsPage,AdminLayout,AdminLoginPage}.tsx`, routed under `/admin` in `App.tsx`, guarded by `RequireRole role="ADMIN"`
- `admin-service/src/modules/admin/controllers/admin.controller.ts` — `GET /admin/dashboard`, `GET /admin/users`, `POST /admin/users/:id/deactivate|reactivate`, `POST /admin/dealers/:id/approve|reject`, `GET /admin/uploads`, `GET /admin/audit-logs`
- Guarded by `JwtAuthGuard`/`RolesGuard`/`@Roles('ADMIN')`. Complete dashboard, user/dealer approval flow, upload job monitoring, and searchable audit logs, fully backed end-to-end.

**Biggest gaps by impact:**

3. **Search index staleness (FR-13.1, FR-13.2)** — editing a listing silently leaves it findable only by its *old* content; a real correctness bug, not just a missing feature.
4. **Dealer self-service UI (FR-58)** — backend is done; no frontend page calls it.
5. **Recommendations (FR-25)** — scaffold only.
