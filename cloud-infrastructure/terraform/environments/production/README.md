# Production environment

Deploys auth-user-service, marketplace-service, admin-service,
notification-service, and web-frontend. **ingestion-service is not deployed**
— see `DEPLOYMENT-GAPS.md` at the repo root for what that would add.

## Before you apply anything

1. **Remote state.** This config has no `backend` block, so it defaults to
   local state — which will contain the generated JWT secret, internal
   service key, and per-service DB passwords in plaintext (Terraform's
   `sensitive` marker only redacts CLI output, not the state file itself).
   Configure an encrypted remote backend (S3 + DynamoDB lock, or Terraform
   Cloud) before running this against a real account.
2. **Credentials.** `aws configure` (or equivalent) with an account that can
   create VPCs, RDS, Lambda, IAM roles, ECR, SES, S3, and CloudFront.
3. **Values only you can supply** — put these in a git-ignored
   `production.auto.tfvars` (matches the repo's existing `*.auto.tfvars`
   gitignore rule):
   ```hcl
   groq_api_key      = "..."               # required
   ses_sender_email  = "no-reply@you.com"  # or ses_domain_name + ses_route53_zone_id
   ```
   Everything else (JWT secret, internal service key, the 4 per-service DB
   passwords) is generated by Terraform — see `modules/secrets`.

## Apply order (image-based Lambdas can't be created against an empty ECR repo)

```
terraform init

# 1. ECR repos only — nothing else exists yet to reference
terraform apply \
  -target=module.auth_lambda.aws_ecr_repository.this \
  -target=module.marketplace_lambda.aws_ecr_repository.this \
  -target=module.admin_lambda.aws_ecr_repository.this \
  -target=module.notification_lambda.aws_ecr_repository.this

# 2. Build + push each service's image to its new repo, tag :latest
#    (or whatever var.image_tag is). See each Dockerfile's CMD for the
#    handler it expects — marketplace/admin/notification need
#    src/lambda/<name>.ts added first (plan item 1); auth already has one.

# 3. Everything else
terraform apply
```

After the first apply, CI updates each function's running image directly
(`aws lambda update-function-code --image-uri ...`) — faster than a full
`terraform apply`, and `modules/lambda` sets `lifecycle.ignore_changes =
[image_uri]` so a later `terraform apply` won't fight CI and roll the image
back to `var.image_tag`.

## One-time database setup (not automated — see why below)

RDS has no `docker-entrypoint-initdb.d` equivalent, and the instance is
`publicly_accessible = false`, so nothing here can run SQL against it
automatically. After `terraform apply`:

1. Reach the database. It's in a private subnet — use AWS Systems Manager
   Session Manager port-forwarding (no bastion host to maintain) or a
   temporary EC2/Cloud9 instance inside the VPC.
2. Get the master credentials from Secrets Manager, at the ARN in this
   config's `database_master_secret_arn` output.
3. Create the 5 per-service roles — mirrors
   `database/docker/init/03-roles.sql`, but with the generated passwords
   from this config's `db_service_role_passwords` output instead of the
   local dev ones, and **no `ingestion_service_role`**:
   ```sql
   CREATE ROLE auth_service_role         LOGIN PASSWORD '<from output>';
   CREATE ROLE marketplace_service_role  LOGIN PASSWORD '<from output>';
   CREATE ROLE notification_service_role LOGIN PASSWORD '<from output>';
   CREATE ROLE admin_service_role        LOGIN PASSWORD '<from output>';
   GRANT CONNECT ON DATABASE vehicle_marketplace TO
     auth_service_role, marketplace_service_role,
     notification_service_role, admin_service_role;
   ```
4. Run `database`'s migrations and grants against the same endpoint
   (`terraform output database_proxy_endpoint`):
   ```
   cd database
   DATABASE_URL=postgresql://<master>@<proxy_endpoint>:5432/vehicle_marketplace npm run migration:run
   npm run grants
   ```
   (`grants.sql` GRANTs to `ingestion_service_role` will fail if that role
   doesn't exist — comment those lines out for this deployment, or run
   `grants.sql` with the ingestion block removed.)

## SES sandbox

A new SES identity can only send to other verified addresses until you
request production access in the SES console (Account dashboard → "Request
production access") — there's no Terraform resource for that request. Real
signups can't receive email until it's granted.

## Known simplifications (see the deployment plan for the full list)

- One Lambda per service, not marketplace's `marketplace-api` +
  `search-api` split.
- Single-AZ NAT Gateway, single RDS instance (no Multi-AZ).
- `admin`'s `execute-api:Invoke` grant is scoped to `"*"`, not the internal
  API's specific ARN — tightening this means breaking the
  iam → api_gateway → lambda → iam cycle documented in `main.tf`.
- Secrets Manager holds the JWT/internal-key/DB-password values as the
  source of truth, but each Lambda also gets them as plain environment
  variables (the application code doesn't fetch from Secrets Manager at
  runtime) — rotating a secret means a `terraform apply` to push the new
  value to the Lambdas, not something that happens automatically.
